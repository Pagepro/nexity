# Client code and performance

Rules for client components in `web/`, each from a measured regression. Indexed from [`web/AGENTS.md`](../../web/AGENTS.md); the short version of each rule is there, the full one is here.

## Client Code & Performance

Every client component costs twice: its JS downloads and runs on every page that
renders it, and React hydrates its DOM. Lighthouse counts both (TBT is 30% of the
mobile score). The rules below each come from a measured regression.
`pnpm lint` runs `pnpm check:client`
(`web/scripts/check-client-boundaries.mjs`), which enforces the mechanical ones.

**Before adding `"use client"`**
- A file needs it only for state, effects, event handlers, browser APIs, or a non-serialisable prop (a render function, a plugin instance). Markup, links, images, CTAs and `stegaClean` logic stay on the server. `HeaderCta` and the desktop comparison table were client-side for no reason.
- Put the boundary as low as possible: the client file is the interactive leaf (a toggle, a form, a carousel), not the section or the header. A client parent turns everything it imports into client code.
- **Never import a server-only renderer into client code** (`check:client` fails): `RichText` ships Portable Text and every block renderer, `FeatureIcon` ships ~30 icons, `@sanity/client` the whole client. Render it on the server and pass it in as a `ReactNode` prop (reference: `TestimonialsSection`, `slides: { key, card }[]`), or import only what you need (`ImpactCalculator/result-row.tsx` takes a lucide component).
- **The same goes for `<Image>`, `ButtonLink` and `cn()`** (`check:client` rules 3–4). `<Image>` brings the URL builder and asset utils, `ButtonLink` brings ArrowLink, Icon, Spinner and tailwind-merge, and `cn()` is tailwind-merge (8.4 KB br plus a class map built during hydration). Pass them in rendered: header `HamburgerMenu ctaSlot`, `ImpactCalculatorClient ctaSlot`, `LogosTrack slides`, `RichTextVideoPlayer poster`. Pricing goes further: the plan cards are server components and only the billing tabs (`PricingPlans`, a context provider) and each card's `PlanPrice` are client code. In client code join classes with `clsx`, and don't write classes that conflict (one branch sets the border colour, the base has no height a caller overrides): `clsx` keeps both and the stylesheet order wins. Allowed: listing cards rendered in the browser from fetched data may use `<Image>` (`IMAGE_IN_CLIENT_ALLOWED` in the script).
- **A static import ships even when nothing renders.** `@next/third-parties`' GTM put `next/script` on every page with no GTM id. GTM now loads through the consent manager (`ui/cookie-consent/consent-manager.tsx`, c15t's `googleTagManager` helper), which is itself deferred until the first interaction or ~5 s, and requests the container only after consent. Gate an optional client feature by not importing it, not by rendering `null`.

**Load client code only where and when it is needed**
- **Section client code goes through `client-lazy.tsx`** (`"use client"` + `dynamic(() => import("./client"))`, SSR kept); a section's server files never import `./client` directly (`check:client` fails). Turbopack otherwise bundles every section's client code into one chunk that every CMS page loads. `dynamic()` on the server section in `map.ts` does **not** split, and a shared library (embla) splits only once **every** section using it goes through a wrapper. See #12.
- **Code that reads layout at mount starts near the viewport.** A widget that measures the DOM on init (embla measures every slide) forces a layout during hydration. Gate it on `useIsNearViewport(ref)` (`@/lib/use-is-near-viewport`, IntersectionObserver, 200 px margin), Astro's `client:visible` idea; the server HTML must already look like the initial state. Reference: `components/ui/carousel.tsx`. A widget inside something hidden (`display: none`, a closed accordion) never intersects, so it never starts: don't gate those. See #13.
- **A library a widget needs only once it runs is `import()`ed after `afterPageLoad()`** (`@/lib/after-page-load`: `load` + the first LCP entry + idle). Embla is the reference (`lib/use-lazy-embla-carousel.ts`, plugins through the carousel's `loadPlugins`); it attaches to the server-rendered DOM without a remount. Not near-viewport alone: a widget at the fold requests its chunk right after hydration, at the end of the longest dependency chain on the page, and Lighthouse's simulated LCP charged that 8 KB chunk 0.4 s. See #17.
- **UI that can wait waits for `InteractionProvider`**: first pointerdown / keydown / scroll, or 5 s then the next idle moment (`DeferUntilInteraction`, used by the cookie banner). Never `requestIdleCallback` alone: it fires right after hydration, inside the load window.
- **Popovers load on intent.** Radix HoverCard/Tooltip load through `useLoadOnIntent` (`@/lib/use-load-on-intent`): the plain trigger renders first and swaps itself for the Radix version (reference: `RichText/RichTextLinkPreview.tsx`, `ComparisonTable/feature-hint.tsx`; keep `shouldFocusTrigger` + `useCloseIfPointerLeftDuringLoad` or the swap loses focus / leaves the popover stuck open). Never import `radix-ui` statically into a component that renders on public pages.
- **Editor-only client code goes behind `next/dynamic`.** A client component that returns `null` outside draft mode still ships its whole import graph when it is statically imported from a layout: `next-sanity/hooks` pulled ~240 KB gz of `@sanity/visual-editing` into every public page.

**Measured and rejected** (don't retry without new evidence): a `<Suspense>` boundary per section (out-of-order streaming, LCP +300 ms with the hero inside, content hidden without JS, no measurable TBT gain); `active: false` on embla (it measures before checking the flag); a `browserslist` change (the flagged polyfills ship regardless). Details: `implemented-fixes.md` → "Tried and reverted".

**PSI's LCP is the bytes that finish before the first paint.** Lighthouse replays every request that finished before the observed LCP over slow 4G. Anything that loads at startup, or makes the first frame slower (Next's blur placeholders did), moves the reported LCP; a second origin adds a handshake. The Lighthouse report's network requests up to the LCP timestamp show this "LCP window" (bytes by type, other origins).

**Verify** a change that touches client code: `pnpm lint` (includes `check:client`), then compare the page's JS against `main` on a production build (`pnpm build && pnpm exec next start`, sum the `<script src>` and script-preload chunks, skipping the `noModule` polyfill; the homepage is ~159 KB gz, a page without interactive sections ~153 KB). For main-thread work, a local Lighthouse run is noisy (±10 points); prefer several cold loads at 6× CPU with the Long Tasks API, or a DevTools trace. `pnpm exec next analyze` maps bytes to modules. Plain `next start` is HTTP/1.1 with six sockets, which delays the scripts and flatters a local Lighthouse LCP: judge PSI changes on a Vercel preview, or locally behind an HTTP/2 + brotli proxy (`implemented-fixes.md` #14–20, "How it was measured").
