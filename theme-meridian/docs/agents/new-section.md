# Creating a new section

The full checklist for a new page-builder section. The `create-section` skill runs it. Indexed from [`AGENTS.md`](../../AGENTS.md); the short version of each rule is there, the full one is here.

## Creating a New Section (full workflow)

**Before step 1:** read the root [`DESIGN.md`](../../DESIGN.md) for how the section looks (tokens, section anatomy, cards, buttons, do's and don'ts) and [`BRAND.md`](../../BRAND.md) for what it says (copy, names and numbers for the fixture and the first instance). Neither is optional: a section that only matches its neighbours drifts from the design system.

0. **Check whether a section already draws it.** Look through `SECTION_META` (`web/src/ui/styleguide/sections-gallery/section-meta.ts`), the Sections Gallery (Studio → **Styleguide** → *Sections*) and `INNER_SECTIONS` (`studio/src/sanity/schemaTypes/fragments/sections.ts`). Reuse that section as is, or add a layout option or a field to it; build a new type only when neither fits (the `content-model-architect` agent helps decide). A near-copy of an existing section is two schemas, two components and two tiles to keep in step.
1. Create schema in `studio/src/sanity/schemaTypes/sections/my-section.ts` (see `studio/AGENTS.md` for schema rules). **Don't name a field `groups`** — it shadows the schema-level `groups` (field-group/tabs) key on `defineType`; use a domain-specific name (e.g. `featureGroups`).
2. Register the type in **two** places: `studio/src/sanity/schemaTypes/index.ts` (sections array) **and** `studio/src/sanity/schemaTypes/fragments/sections.ts` — add `{ type: "my-section" }` to `INNER_SECTIONS` **and** the matching `insertMenu` group (usually `content`). **Skipping `fragments/sections.ts` is the #1 silent gap: the schema compiles and typegens, but the section never appears in any page's insert menu** (editors can't add it).
3. Add a conditional branch to `SECTION_BRANCHES_QUERY` in `web/src/sanity/lib/queries.ts`
4. Run `pnpm --filter @meridian/web ts:typegen`
5. Create component in `web/src/ui/sections/MySectionName/index.tsx` — use `section` class on `<section>` element for horizontal padding (see `web/AGENTS.md` Section Layout & Padding)
6. Register component in `web/src/ui/sections/map.ts` `INNER_SECTION_MAP` (alphabetical order) — the top-level `SECTION_MAP` in `index.tsx` spreads it and adds the `shared-section-ref` wrapper
7. **Restart the Studio AND the web dev server before seeding/editing a document that uses the new section.** A running Studio loaded with the *old* schema does not recognize the new section type and will **silently strip it from the document on save/sync** (seeded content "disappears"); a stale web dev server filters/under-fetches it via `SECTION_MAP`/`SECTION_BRANCHES_QUERY`.
8. **Add the section to the Sections Gallery** (`web/src/ui/styleguide/sections-gallery/`, surfaced in Studio under the **Styleguide** top-nav tool → *Sections*). The catalog is derived from the generated section-type union, so after typegen `pnpm typecheck` **fails** until you wire the new type in — it can't silently disappear:
   - Add the `_type` string to the `SECTION_TYPES` array in `fixtures-registry.ts` (the `_AssertComplete` drift guard errors otherwise).
   - Add a `SECTION_META` entry in `section-meta.ts` — `title`, `description`, a hand-authored `accepts` hint, and a `group` (`SECTION_META` is an exhaustive `Record<SectionType, …>`, so a missing key is a compile error). **`accepts` is hand-authored, not schema-introspected** — the web app must never import the Studio schema runtime (package-boundary rule).
   - Add a co-located `gallery-fixture.ts` next to the component (`export const <type>Fixture = {…} satisfies ExtractSectionProps<"<type>">`) and register it in `SECTION_FIXTURES`. Keep it **pure data** — import only `ExtractSectionProps` (type) and the helpers from `mock-image.ts` (`mockImage`, or `imageFromUrl` with `CDN_BASE`) for image fields; never import the section component. The images are seeded assets, so the previews need `pnpm seed`. Without a fixture the gallery shows a "Needs fixture" placeholder (valid, but no live preview). Fixtures are the **resolved GROQ shape** (dereferenced refs, expanded image `asset`) — copy `HeroSection/gallery-fixture.ts` as the template. **Typegen runs with `--enforce-required-fields`, so every *optional* schema field is generated as `field: T | null` (required *and* nullable) — the fixture must set `field: null` explicitly on every array item that omits it** (e.g. `hint: null` on each row), or `pnpm typecheck` fails with "Property 'x' is missing".
9. **Declare what the section adds to the page's JSON-LD graph** by adding an entry in `SECTION_SCHEMA_CONTRIBUTORS` (`web/src/lib/schema-org/build-graph.ts`): either a contributor function, or `null` with a one-line reason. **`pnpm typecheck` fails until you do**, because the registry is `satisfies Record<SectionType, …>` over the generated section union, the same drift guard the gallery uses. Most sections are `null`, since a hero, a stats band or a CTA doesn't describe a schema.org entity. `faq` contributes `Question` nodes and makes the page an `FAQPage`. A contributor must be pure (data in, nodes out, no React, no `@/` value import, so the `.test.mts` runner can load it). It receives the section's projected fields and the page URL. If it reads a field, make sure the section's `SECTION_BRANCHES_QUERY` branch projects it.
10. **Give the section a Markdown serializer** for AI agents (`/x.md`): a co-located `markdown.ts` exporting a `SectionMarkdownSerializer<SectionData<"<type>">>`, registered in `SECTION_MARKDOWN_SERIALIZERS` (`web/src/lib/markdown/section-serializers.ts`). **`pnpm typecheck` fails until you do** (same `satisfies Record<SectionType, …>` guard). It says what the component shows: a layout that hides a field hides it here too, images become their alt text (`imageHint`), an interactive widget a `presenceHint`, copy the component renders as literals moves to the section's `constants.ts` so both read it. Pure like the contributor above (`import type` from the component side, no `next-sanity`); the test suite runs every gallery fixture through it. See `docs/guides/markdown-for-agents.md`.
11. Run `pnpm typecheck` — the fixture's `satisfies ExtractSectionProps<"…">` and the registry's bidirectional assertions catch schema drift at compile time.
12. **Capture the section's insert-menu tile** with `pnpm dev` running: `/sanity-module-catalog --only=<type>` (or `node .agents/skills/sanity-module-catalog/scripts/capture.mjs --project=. --only=<type>`). It writes `web/public/admin/thumbnails/<type>.webp`; look at the file before committing it. Without it the grid view of "Add item…" shows a blank tile.
13. **Update `docs/FEATURES.md`** — add the new section to the page-builder blocks table (and adjust the block count). That file is the editor/marketer-facing feature inventory; unlike the gallery, nothing fails the build when it's stale, so this checklist step is the only guard.
