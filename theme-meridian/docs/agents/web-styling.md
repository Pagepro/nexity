# Styling (Tailwind CSS v4)

The Tailwind mechanics behind `DESIGN.md`. Indexed from [`web/AGENTS.md`](../../web/AGENTS.md); the short version of each rule is there, the full one is here.

## Styling (Tailwind CSS v4)

- **Read the root [`DESIGN.md`](../../DESIGN.md) first.** It is the visual contract for every new section or component: the token set, the type scale, the section anatomy, the double frame, button/chip/card recipes, the marker and imagery rules, and the do's and don'ts. The bullets below are the Tailwind mechanics behind it. When a request (a mockup, a screenshot, review feedback) conflicts with `DESIGN.md`, follow `DESIGN.md` and raise the conflict; when `DESIGN.md` conflicts with Figma, Figma wins and `DESIGN.md` gets updated in the same PR.
- **Colors are the shadcn/ui OKLCH "Stone" palette.** Semantic tokens (`background`, `foreground`, `card`, `card-muted`, `popover`, `primary`, `secondary`, `muted`, `accent`, `destructive`, `border`, `input`, `ring`, `chart-1..5`, `sidebar-*`) live in `:root` (light) and the `dark-palette` variant (dark, applied by `.dark`) and are bridged to Tailwind utilities via `@theme inline` in `app.css`. Use `bg-primary`/`text-primary-foreground`, `bg-muted`/`text-muted-foreground`, etc. — there is **no** `brand-olive` token anymore (dropped → `primary`).
- **A new color enters `app.css` only when it exists as a variable in Figma (the design-system source of truth).** HTML mockups, product-UI screenshots and "review feedback" are not token sources. If a reference needs a color outside the current list (Stone semantic tokens + the `accent-peach`/`-sage`/`-rose` markers), do this first: (1) raise it with the designer and add the variable in Figma; (2) declare the token in OKLCH with a `.dark` variant, never a raw hex; (3) add its `COLOR_META` entry in `token-metadata.ts`; Until then, use the closest semantic token (`foreground` / `muted-foreground` / `primary`). A one-off color added straight from a mockup is the usual way the palette drifts.
- **`--card` is pure white (`oklch(1 0 0)`), identical to `--background`.** A Figma section painted with its `base/card` variable (`#fafaf9`, a *tinted* panel) will look like it has **no background** if you map it to `bg-card` — the tint vanishes against adjacent white sections. Map Figma `base/card` (`#fafaf9` / stone-50) to the dedicated **`bg-card-muted` / `border-card-muted`** token (`--card-muted` in `app.css`: light `oklch(0.985…)` = `#fafaf9`, dark kept slightly lighter than `--card` so it stays distinct). Do **not** reach for `bg-muted` (`#f5f5f4` / stone-100 is one step too dark) or `bg-card` (pure white) for this tint — both are silent fidelity misses. Reserve `bg-muted` for genuinely greyer blocks (Figma `#f5f5f4`). Never hardcode the literal `#fafaf9`.
- **Watch for multi-stroke ("double") borders in Figma — they're easy to miss.** A Figma card frame often combines a thick `border` in the **background color** (the visible gap) with a 1px `boxShadow`/inset stroke on each side (e.g. `border-4 border-white` + outer `0 0 0 1px stone-200` + inner stone-200 = outer line / white gap / inner line). Reproduce it with tokens, not arbitrary values: `card-frame border-4 border-background shadow-card`. `shadow-card` (`--shadow-card` in `app.css` = `0 0 0 1px var(--border)`) draws only the OUTER line; the inner hairline comes from the `.card-frame` class, a `::after` overlay painted on top of the content so full-bleed images can't cover it (an `inset` box-shadow would sit under them). For a borderless card set `[--card-frame-gap:0px]`, and match a non-default radius with `[--card-frame-radius:var(--radius-…)]`. Reference: `FeatureGrid/feature-card.tsx`. When checking a design, always inspect a card's `border` **and** `effects`/`boxShadow` together — a single `border` utility usually under-renders the frame.
- **To glue an `absolute` child (e.g. a product image) to a card's bottom/right edge, put the card's `min-h` on the inner flex/grid — not on the card.** A `min-h` on the card makes the *card* tall, but its single flow child (the grid) stays at content height and is top-aligned, so an image anchored `bottom-0` inside that grid stops *above* the card's bottom edge, leaving a gap. Fix: make the card `flex`, give the inner grid `w-full` + the `min-h`, so the grid stretches to the full card height and `inset-y-0`/`bottom-0` reach the real edges. Use a CSS-var height token (`min-h-[var(--…)]` in `app.css`, the `--hero-height` pattern), never an arbitrary px value. Reference: `CtaBanner/index.tsx` (image glued right/bottom, `left-8` inset on mobile, `lg:top-16` 4rem top gap; wrapper height ramps `min-h-64 md:min-h-96 lg:min-h-0`). Note `rounded-xl` = 16px but `rounded-2xl` = **22px** (`--radius-2xl: 1.375rem`) — check the token before matching a Figma radius.
- **A carousel of bordered/elevated cards clips the border — pad the track.** The trimmed `@/components/ui/carousel` viewport is `overflow-hidden` (embla requires it), which shaves a card's `shadow-card` outer 1px stroke (and any `ring`/`outline`) at **all four** track edges. Add `p-0.5` (2px) to `CarouselContent` so the decoration clears the clip. The primitive ships **no** dots/arrows (no shadcn `Button` here) — build dot pagination from the embla `api`: gate on `snapCount > 1` (`api.scrollSnapList().length`, synced on `select` **and** `reInit`) so dots appear only when content scrolls and auto-hide when all cards fit. For a section that's a 3-up grid on desktop and a carousel below, use **one** carousel with `basis-full md:basis-1/2 lg:basis-1/3` (no `useMediaQuery`, no duplicate markup; at `lg` all fit → `snapCount === 1` → no dots). Reference: `TestimonialsSection/client.tsx`.
- **Font is Mona Sans SemiExpanded** (single family, loaded via `next/font/local` in `ui/fonts.ts` → `--font-mona-sans`, exposed as `font-sans`/`font-heading`). No Poppins/Inter. Served as **WOFF2** subsets (never the TTFs), two per weight split by `unicode-range`: **core** (ASCII + the punctuation the copy uses, ~13 KB) and **ext** (rest of Latin-1 + Latin Extended-A, ~10 KB, fetched only on a page that contains such a character). Only the 400/500 core files are preloaded; the other `localFont` calls are pinned to the same family via `declarations`. The fallback is the per-weight, metric-matched `"monaSans Fallback"` faces in `app.css` (`adjustFontFallback: false`). Adding a weight or a character range = regenerate the subsets with `pyftsubset` (fontTools; keep the ranges in `fonts.ts` in sync) and, for a weight, add a fallback face with a measured `size-adjust`.
- All non-color theme tokens are in `web/src/styles/app.css` under `@theme`
- No arbitrary Tailwind values (`[23px]`) — add variables to `app.css` instead (e.g. the `--text-NN` size ladder → `text-16`, `text-36`, `text-44`)
- **Tailwind v4 scans Markdown too — never paste a literal Figma class into docs.** A class example like `text-[length:var(--text/sm/font-size,14px)]` in a `.md` file gets compiled into invalid CSS (`/` in a custom-property name) and breaks the whole build. `app.css` has `@source not "../../../**/*.md";` to exclude docs — keep it.
- Never use `[&_p]` or similar child-targeting Tailwind selectors to override RichText block styles — text styling is CMS-driven via block style selection (body-1, body-2, etc.)
- Text size and line-height in sections should be controlled by selecting the appropriate block style in the CMS, not by wrapping RichText with override classes
- **Never use `@utility` for CSS custom property overrides.** Tailwind v4's `@theme` registers variables with `@property` that prevents inheritance. Use a plain CSS class (e.g., `.dark`) to override the color tokens so children cascade correctly.
- **`cn()`/tailwind-merge silently drops a custom `text-NN` size when it shares a class list with a `text-{color}` utility.** twMerge groups all `text-*` together and only recognizes *standard* size tokens (`text-sm`, `text-[length:…]`), so it treats our custom `text-12`/`text-16`/… as conflicting with `text-foreground`/`text-muted-foreground` and keeps only one — the element silently falls back to the inherited 16px. **Fix:** put the `text-NN` size on a parent and let children inherit (color-only classes in the child's `cn`), or keep the size in a plain non-`cn` className. Always confirm with `getComputedStyle(el).fontSize` — a present class string is not proof it survived the merge. Reference: `BlogListingSection/category-tabs.tsx`.
- Add colors, typography and other values that can be stored in theme to `@theme`
- **After adding/removing a design token in `app.css`, keep the `/styleguide` page in sync.** The styleguide reads tokens straight from `app.css` at build time (`web/src/ui/styleguide/parse-design-tokens.ts`), but each section either *pattern-matches* or uses a *curated allowlist* — and the curated ones silently drop a token that has no entry:
  - **Auto (no action):** the numeric `--text-NN` ladder, `--radius-*`, and `--index-N` are pattern-matched (`token-metadata.ts` `*_PATTERN`) and appear on their own.
  - **Curated (must add an entry):** a new **color** needs a `COLOR_META` entry (+ a `COLOR_GROUPS` group if it's a new group); a new **layout/spacing** token needs a `LAYOUT_META` entry; a new **shadow** needs a `SHADOW_META` entry. All in `web/src/ui/styleguide/token-metadata.ts`. Skip this and the token won't render on `/styleguide`.
  - **New styleguide _section_:** add `sections/<name>.tsx` (copy the `(tokens) → filter → DocSection + primitives` pattern), register it in `styleguide/index.tsx` (import + element, manual `number="/N"`), and add a `{ id, label }` to `STYLEGUIDE_SECTIONS` in `styleguide-nav.tsx` (the `id` must match the `DocSection` `id`).
- Add CSS transitions when elements are animated (state changes from active to inactive)
- **Animating `translate-*`/`scale-*`/`rotate-*`? Use `transition-all`, not `transition-transform` or `transition-[transform,…]`.** In Tailwind v4 these utilities set the standalone CSS `translate`/`scale`/`rotate` properties (not `transform`), so a `transform`-only transition leaves them un-transitioned and they **jump**. `transition-all` covers `translate` + `opacity` together (and isn't an arbitrary value). When measuring in DevTools, read `getComputedStyle(el).translate`, not `.transform`.
- **Don't gate small, deliberate micro-interactions behind a JS `prefers-reduced-motion` check** — it makes the effect look broken in automated browsers (the chrome-devtools MCP Chrome reports `reduce: true` by default) and for Reduce-Motion users. Reserve motion-reduction for large parallax/zoom/autoplay, and handle it in CSS via the `motion-reduce:` variant.

### Design Fidelity (Figma → Implementation)

When building or restyling a section from Figma, **match the design precisely the first time** — missing elements and "close enough" sizes cause avoidable review round-trips. Before calling a section done:

1. **Enumerate every element in the Figma node and account for each one.** Pull `get_design_context` (exact text + structure) — never eyeball the screenshot, which is low-res and drops detail. Walk the node's children top-to-bottom and confirm each appears in the implementation: eyebrow/meta, title, **author/byline**, excerpt, buttons, dividers, badges. If the design shows a field the schema lacks (e.g. an author line), **add the field and flag it** — don't silently omit it or substitute a different field.
2. **Read sizes from Figma, don't guess.** For each text/spacing/dimension, take the literal Figma value (font-size, container max-width, image aspect ratio, gaps/margins) and map it to the nearest token: e.g. `576px → max-w-xl`, `12px → text-12`, `4/3 image → aspect-[4/3]`. `get_design_context` reports them as `text-[length:var(--text/sm/font-size,14px)]` etc.; `get_variable_defs` resolves the rest. Don't approximate `max-w-2xl` (672) when the design says 576.
3. **Verify computed values in the browser, not the class string.** After rendering, measure with `getComputedStyle(el)` / `getBoundingClientRect()` and compare against the Figma numbers — font-size, element widths/%, aspect ratios, top/bottom gaps. This catches both dropped classes (see the tailwind-merge `text-NN` trap above) and wrong-token approximations.
4. **Check alignment and fill intent.** "Image spans the card top-to-bottom" means `items-stretch` + `aspect-auto` + fill (not a fixed aspect that leaves gaps); "button at the bottom" means `self-stretch` + `justify-between`. Confirm a column's child actually reaches the parent's edges.
5. **Re-screenshot at mobile + desktop and diff against the Figma frame** before declaring done. Treat the Figma node as the acceptance bar, not an approximation.

### Section Layout & Padding

The `section` CSS utility (`@utility section` in `app.css`) is a **centered page container**: `max-width: var(--width-container)` (1280px, Figma `max-w-7xl`), `margin-inline: auto`, and responsive side padding via `--section-padding-inline` (`20px` mobile → `60px` from the `1024px` desktop breakpoint). The 1280px is the design-frame width and the padding sits **inside** it (content maxes at ~1160px on desktop).

- **Always use `section` class** for the content container — on the `<section>` element, or on an inner content wrapper for full-bleed sections (e.g. `HeroSection`, whose `<section>` carries the background image while the overlay content div uses `section`). Never use raw `px-*` / `max-w-* mx-auto` to reproduce this.
- **Header, footer, and all sections share the `section` container** so content edges align across the entire page. Full-bleed backgrounds (header bar, footer bar, dark `.dark` wrappers, hero images) stay 100% wide — only the inner content uses `section`.
- **Tune the container globally** via the three theme tokens in `app.css` (`--width-container`, `--section-padding-inline`, `--section-padding-inline-desktop`) — never hardcode the width or gutters per section.
- **Narrower content** (e.g., `max-w-xl` for text columns) still goes on an inner `<div>` inside the `section` container, not on the `section` element itself.

### Section Color Inversion

Dark sections use the shadcn **`.dark`** class (plain CSS class, NOT `@utility`). `.dark` re-declares the OKLCH color tokens (`--background`, `--foreground`, …) to their dark values, so all children (`.richtext`, buttons, borders) automatically resolve to inverted colors, and `dark:` utility variants work inside.

- Applied by the `Sections` renderer (`ui/sections/index.tsx`, classes from `getSectionThemeClassName` in `ui/sections/section-theme.ts`) when `section-options.colorTheme === "dark"` — the wrapper gets `section-themed dark bg-background text-foreground` (the `bg`/`text` paint the wrapper itself with the now-dark tokens; `.dark` alone only flips the variables). **`"light"` paints it `section-themed bg-background`.** Unset paints nothing (it is NOT treated as Light), which is why `colorTheme` has no `initialValue`.
- **A band's OWN surface is `bg-section-surface` (default `--card-muted`) or `bg-section-surface-muted` (default `--muted`), never a bare `bg-card-muted`/`bg-muted` on its `<section>`.** `section-themed` sets `--section-surface: transparent`, so the editor's choice wins for every section type. A bare surface class sits inside the wrapper and silently disables the Color theme for that type (Light stayed grey; Dark showed the band's `--card-muted` as a second, lighter dark). Card-level greys (image placeholders, table fills) are not band surfaces and stay as they are.
- **A `-z-10` background layer needs `isolate` on the box it belongs to** (Hero, CtaBanner, RichTextCallout have it). Without a stacking context the image sinks behind the nearest ancestor that paints a background — i.e. behind a themed wrapper.
- **Plain CSS in `app.css` reads the RAW tokens (`var(--foreground)`), never the `--color-*` bridge.** `@theme inline` declares `--color-foreground: var(--foreground)` on `:root`, where it resolves once and inherits as the light value, so a `.dark` scope never reaches it. Utilities are unaffected (they inline `var(--foreground)`).
- CTA variants: use `primary-outline` (foreground-based, light in dark context), NOT `light-outline` (background-based, inverts wrong)
- The old bespoke `.section-inverted` class was removed in favor of `.dark`.

### Header & Footer Layout

- **The header is a fixed transparent overlay** (`HeaderContent`'s `Wrapper` = `fixed inset-x-0 top-0 z-50`), sitting on top of content rather than in flow. `header/Wrapper.tsx` (`"use client"`) keeps it transparent at the top and animates to `bg-background border-b border-border` once `window.scrollY > 4`, and forces that solid surface while the mobile menu is open (`[.header-open_&]:bg-background`). The border is always present but `border-transparent` until scrolled, so only its colour animates.
- **Header text is `text-foreground`, and the bar resolves the DARK palette while transparent over a dark first section.** The bar lives in the layout and otherwise resolves `:root`, so over a Dark hero its links, hover washes and CTA were dark-on-dark. The `dark-palette` custom variant in `app.css` applies the `.dark` token block to `.header-bar:not(.header-scrolled)` when `body:has(.dark > [data-first-module="true"][data-header-overlay=…])` and the mobile menu is closed — pure CSS, so SSR is correct with no flash. A section that bleeds under the bar must set `data-header-overlay` (`"always"`, or `"below-3xl"` for the product hero, which is a contained card below the bar from 3xl); HeroSection does. Header hover fills use the opaque `bg-button-ghost-hover` token pair, not a `foreground/5` wash. CAVEAT: a raster `site.logo` cannot recolour, and a dark hero **image** with an unset theme still gets the light palette — set the hero's Color theme to Dark for light header text.
- **Because the header is out of flow, `<main>` carries `pt-[var(--header-height)]`** (`(frontend)/layout.tsx`) so non-hero pages clear the navbar. `--header-height` is measured live by a `ResizeObserver` in `header/Wrapper.tsx`. **The CSS fallback in `app.css` must equal the real bar height** (53px below `lg`, 65px from `lg`): when they differ, the post-hydration write moves the whole page (a layout shift on every route). Re-measure and update it whenever header padding or CTA size changes.
- **A first-module Hero bleeds its background up under the navbar** via `[&[data-first-module=true]]:-mt-[var(--header-height)]` (cancels `<main>`'s top padding so the image starts at the viewport top), while `[&[data-first-module=true]]:pt-[calc(var(--header-height)+…)]` keeps the hero's *content* below the navbar. See `HeroSection/index.tsx`.
- **Header and footer are no longer dark.** The footer uses `bg-card-muted text-card-foreground` (`footer/index.tsx`) — a light tinted Stone surface (`#fafaf9`), not the old dark `bg-foreground`. Don't wrap header/footer in `.dark`.
